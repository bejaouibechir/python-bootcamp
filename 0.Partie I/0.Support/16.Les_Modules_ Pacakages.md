# 1️⃣ Pourquoi modulariser un projet ?

Dans un projet réel :

- Séparation des responsabilités

- Réduction du couplage

- Réutilisabilité

- Maintenabilité

- Tests unitaires simplifiés

# 2️⃣ Module : définition concrète

Un module est simplement un fichier `.py`.

Tout au long de ce document, nous construisons progressivement une application de gestion de stock **StockPro**.

```
stockpro/
    operations.py
    main.py
```

**operations.py**

```python
"""
Module d'opérations pour la gestion de stock StockPro.
Expose des fonctions réutilisables de calcul.
"""

def total_stock(quantite, prix_unitaire):
    """Calcule la valeur totale d'un article en stock."""
    return quantite * prix_unitaire

def appliquer_remise(prix, taux):
    """Applique une remise sur un prix. taux entre 0 et 1."""
    return prix * (1 - taux)

TVA = 0.20
```

**main.py**

```python
"""
Script principal StockPro utilisant le module operations.
"""

import operations

valeur = operations.total_stock(50, 12.99)
prix_remise = operations.appliquer_remise(valeur, 0.10)

print(f"Valeur stock    : {valeur:.2f} €")
print(f"Après remise    : {prix_remise:.2f} €")
print(f"TVA appliquée   : {operations.TVA}")
```

# 3️⃣ Les différentes formes d'import

```python
"""
Quatre formes d'import — chacune avec son cas d'usage.
"""

# Import complet — accès via namespace
import operations
print(operations.TVA)

# Import ciblé — accès direct
from operations import total_stock
print(total_stock(10, 5.99))

# Import avec alias — raccourci pratique
import operations as ops
print(ops.appliquer_remise(100, 0.15))

# Import élément avec alias
from operations import total_stock as calculer
print(calculer(20, 3.50))

# À éviter — pollution d'espace de noms
# from operations import *
```

# 4️⃣ Espace de noms — namespace

Chaque module possède son propre espace de noms.
Deux modules peuvent définir des variables de même nom sans collision.

```
stockpro/
    entrepot_paris.py
    entrepot_lyon.py
    main.py
```

**entrepot_paris.py**

```python
stock = 150    # unités disponibles à Paris
seuil = 20     # seuil d'alerte Paris
```

**entrepot_lyon.py**

```python
stock = 80     # unités disponibles à Lyon
seuil = 10     # seuil d'alerte Lyon
```

**main.py**

```python
"""
Les deux modules coexistent sans collision de noms.
"""

import entrepot_paris as paris
import entrepot_lyon  as lyon

print(f"Paris : {paris.stock} unités (seuil {paris.seuil})")
print(f"Lyon  : {lyon.stock} unités (seuil {lyon.seuil})")

if paris.stock < paris.seuil:
    print("Alerte stock Paris")
```

### La notion du PYTHONPATH

`PYTHONPATH` est une variable d'environnement qui permet d'ajouter des répertoires supplémentaires à `sys.path`, afin que Python puisse y trouver vos modules et packages lors d'un `import`.

**Ordre de résolution complet :**

```
1. Répertoire du script lancé
2. PYTHONPATH  ← votre extension personnalisée
3. site-packages (modules installés via pip)
4. Chemins système Python
```

**Définir PYTHONPATH selon l'OS :**

```bash
# Linux / macOS — session courante
export PYTHONPATH=/chemin/vers/mon_projet:/autre/dossier

# Windows (cmd)
set PYTHONPATH=C:\mon_projet;C:\autre_dossier

# Temporairement pour une seule commande
PYTHONPATH=/chemin/vers/mon_projet python run.py
```

**Cas d'usage concret avec StockPro :**

```
workspace/
    libs/
        formattage.py   ← bibliothèque maison non installée via pip
    run.py
```

**formattage.py** — bibliothèque maison dans `libs/`

```python
"""
Utilitaires de mise en forme pour StockPro.
Fichier non installé via pip — accessible via PYTHONPATH.
"""

def afficher_euros(valeur: float) -> str:
    """Formate un nombre en chaîne monétaire lisible."""
    return f"{valeur:,.2f} €"

def afficher_alerte(nom: str, stock: int) -> str:
    return f"[ALERTE] {nom} — seulement {stock} unités restantes"
```

# 6️⃣ Emplacements des packages — où Python installe les modules

Quand on fait `pip install pandas` ou `import os`, Python sait exactement où trouver ces modules.
Comprendre les **emplacements physiques** sur le disque évite des heures de débogage sur des erreurs d'import.

## Les trois zones d'installation

```
Zone 1 — Bibliothèque standard (livrée avec Python)
    Windows : C:\Python313\Lib\
    Linux   : /usr/lib/python3.13/
    Contenu : os, sys, json, csv, re, datetime...

Zone 2 — Bibliothèques installées via pip (site-packages)
    Windows : C:\Python313\Lib\site-packages\
    Linux   : /usr/lib/python3/dist-packages/
    Contenu : pandas, requests, openpyxl, customtkinter...

Zone 3 — Votre projet (code local)
    Partout : le dossier de votre script ou PYTHONPATH
    Contenu : stockpro/, operations.py, services.py...
```

## Localiser un module sur le disque

```python
# Trouver l'emplacement physique de n'importe quel module importé
import os
import csv
import pandas as pd
import stockpro.services as svc

# __file__ contient le chemin absolu du fichier .py du module
print("os       :", os.__file__)
# → C:\Python313\Lib\os.py                          (bibliothèque standard)

print("csv      :", csv.__file__)
# → C:\Python313\Lib\csv.py                         (bibliothèque standard)

print("pandas   :", pd.__file__)
# → C:\Python313\Lib\site-packages\pandas\__init__.py  (pip installé)

print("services :", svc.__file__)
# → C:\Users\DELL\Desktop\mon code\stockpro\services.py  (votre projet)
```

- **`__file__`** : attribut présent sur tout module importé — indique son chemin absolu sur le disque
- **`Lib\`** : bibliothèques standard livrées avec Python, **jamais modifiées manuellement**
- **`site-packages\`** : tout ce qu'installe `pip install` — chaque bibliothèque dans son propre sous-dossier
- **votre projet** : trouvé via `PYTHONPATH` ou le répertoire courant — toujours prioritaire sur `site-packages`


```
    main.py
```

```python

```


- **diagnostic rapide** : `print(module.__file__)` révèle immédiatement d'où vient le module chargé

# 6️⃣ bis — `__pycache__` — le cache bytecode de Python

Dès qu'on importe un module Python, un dossier `__pycache__` apparaît à côté du fichier `.py`.
Beaucoup de débutants l'ignorent ou s'en méfient — il est pourtant indispensable pour les performances.

## Ce qui se passe à l'import

```
Première exécution :
    Python lit operations.py  →  compile en bytecode  →  écrit operations.cpython-313.pyc
    Python exécute le bytecode en mémoire

Exécutions suivantes :
    Python vérifie si operations.py a changé (date de modification)
    Si non changé → charge directement operations.cpython-313.pyc  (plus rapide)
    Si changé     → recompile et met à jour le .pyc
```

```
stockpro/
    __init__.py
    operations.py
    services.py
    __pycache__/                        ← créé automatiquement par Python
        __init__.cpython-313.pyc        ← version compilée de __init__.py
        operations.cpython-313.pyc      ← version compilée de operations.py
        services.cpython-313.pyc        ← version compilée de services.py
```

- **`.pyc`** : fichier **Python Compiled** — version binaire optimisée, non lisible directement
- **`cpython-313`** : indique l'interpréteur (CPython) et la version Python (3.13) — évite les conflits si plusieurs versions Python coexistent
- **création automatique** : Python gère `__pycache__` seul — on ne crée ni modifie jamais ces fichiers manuellement
- **gain de performance** : charger un `.pyc` est 3 à 5 fois plus rapide que relire et compiler un `.py`

## Observer **pycache** en pratique

```python
# operations.py
"""Module de calculs StockPro."""

TVA = 0.20

def total_stock(quantite: int, prix: float) -> float:
    """Calcule la valeur totale d'un lot."""
    return quantite * prix

def appliquer_tva(prix: float) -> float:
    """Applique la TVA sur un prix HT."""
    return prix * (1 + TVA)
```

```python
# main.py
import operations                  # ← à ce moment, Python crée __pycache__

print(operations.total_stock(50, 12.99))
print(operations.appliquer_tva(100))
```

```powershell
# Avant d'exécuter main.py :
# stockpro/
#     operations.py
#     main.py

py main.py

# Après l'exécution :
# stockpro/
#     operations.py
#     main.py
#     __pycache__/
#         operations.cpython-313.pyc   ← apparu automatiquement
```

```

120.0
```

## Inspecter le contenu de **pycache** depuis Python

```python
# Voir le chemin du .pyc associé à un module importé
import operations
import importlib.util

spec   = importlib.util.find_spec("operations")
chemin = spec.cached               # chemin vers le .pyc
source = spec.origin               # chemin vers le .py source

print("Source  :", source)
# → C:\...\stockpro\operations.py

print("Compilé :", chemin)
# → C:\...\stockpro\__pycache__\operations.cpython-313.pyc

# Vérifier si le cache est plus récent que la source
import os
source_date  = os.path.getmtime(source)
compile_date = os.path.getmtime(chemin)
print("Cache à jour :", compile_date >= source_date)
# → Cache à jour : True
```

## Forcer la recompilation

```python
# Supprimer le cache d'un module pour forcer la recompilation au prochain import
import os
import glob

def vider_pycache(dossier: str = ".") -> int:
    """
    Supprime tous les fichiers .pyc du dossier __pycache__.
    Utile pour forcer une recompilation propre.
    Retourne le nombre de fichiers supprimés.
    """
    pattern  = os.path.join(dossier, "**", "*.pyc")
    fichiers = glob.glob(pattern, recursive=True)
    for f in fichiers:
        os.remove(f)
        print(f"  Supprimé : {f}")
    return len(fichiers)

nb = vider_pycache("stockpro")
print(f"\n{nb} fichier(s) de cache supprimé(s)")
# → Supprimé : stockpro\__pycache__\operations.cpython-313.pyc
# → Supprimé : stockpro\__pycache__\services.cpython-313.pyc
# → 2 fichier(s) de cache supprimé(s)
# Au prochain import, Python recompile depuis les .py
```

```powershell
# Depuis le terminal — supprimer tous les __pycache__ du projet (Windows)
Get-ChildItem -Recurse -Directory -Filter "__pycache__" | Remove-Item -Recurse -Force

# Linux / macOS
find . -type d -name __pycache__ -exec rm -rf {} +
```

## Désactiver la création du cache (rare)

```python
# Lancer Python sans créer de __pycache__ (option -B)
# Utile sur des systèmes en lecture seule ou pour le débogage
```

```powershell
py -B main.py           # aucun __pycache__ créé pendant cette exécution

# Ou définir la variable d'environnement pour toujours désactiver
$env:PYTHONDONTWRITEBYTECODE = "1"
py main.py
```

```python
# Depuis le code Python
import sys
sys.dont_write_bytecode = True   # à placer AVANT tout import
import operations                # aucun .pyc créé
```

- **`-B`** : option de ligne de commande — pratique pour un script ponctuel
- **`PYTHONDONTWRITEBYTECODE=1`** : variable d'environnement — s'applique à toute la session
- **`sys.dont_write_bytecode = True`** : depuis le code — doit être placé avant tout import
- **cas d'usage** : déploiements en lecture seule, images Docker minimales, débogage de problèmes de cache

## Récapitulatif — Ce qu'il faut retenir sur **pycache**

| Question                             | Réponse                                                   |
| ------------------------------------ | --------------------------------------------------------- |
| Qui crée `__pycache__` ?             | Python automatiquement, à chaque import                   |
| Peut-on le supprimer ?               | Oui sans risque — Python le recrée au prochain import     |
| Faut-il le versionner (git) ?        | Non — ajouter `__pycache__/` dans `.gitignore`            |
| Pourquoi `cpython-313` dans le nom ? | Pour coexister avec d'autres versions Python              |
| Le `.pyc` remplace-t-il le `.py` ?   | Non — le `.py` reste la source de vérité                  |
| Gain de performance réel ?           | Surtout visible sur les gros packages (pandas, Django...) |

```
# .gitignore — lignes standard pour un projet Python
__pycache__/
*.pyc
*.pyo
.venv/
```

> 💡 Règle simple : **ignorer `__pycache__` dans git, ne jamais le modifier manuellement, le supprimer uniquement si un bug de cache suspect est suspecté** (situation très rare).

# 7️⃣ Module exécutable vs importable

Un même fichier `.py` peut jouer deux rôles : être **lancé directement** (`python calcul_stock.py`) ou être **importé** par un autre module. La variable `__name__` permet de distinguer les deux cas.

```
stockpro/
    calcul_stock.py
    rapport.py
```

    Voici un exemple de module lancé directement

**calcul_stock.py**

```python
"""
Module StockPro : calculs de valorisation.
Peut être exécuté directement ou importé.
"""

def valoriser(quantite: int, prix: float) -> float:
    """Calcule la valeur totale d'un lot."""
    return quantite * prix

if __name__ == "__main__":
    # Exécuté uniquement si lancé directement : python calcul_stock.py
    print("Test interne :", valoriser(100, 9.99))
```

if **name** == "**main**":

cela signifie :

**exécuter le code uniquement si le fichier est lancé directement, pas lorsqu’il est importé.**

Supposons maintenant que le **calcul_stock.py** est importé par le code suivant

**rapport.py**

```python
"""
Import du module calcul_stock.
Le bloc __main__ ne s'exécute pas à l'import.
"""

import calcul_stock

valeur = calcul_stock.valoriser(200, 4.50)
print(f"Valorisation du lot : {valeur:.2f} €")
```

Le message **"Test interne" n’apparaît pas** parceque la condition :

if **name** == "**main**":

est **fausse**, donc le test interne ne s’exécute pas.

# Pourquoi on utilise cette technique

Elle sert à séparer :

• **le code réutilisable** (fonctions, classes)  
• **le code de test ou de démonstration**

Ainsi un module peut être :

• utilisé comme bibliothèque  
• exécuté comme programme autonome

> Ces noms sont appelés **noms spéciaux** ou **dunder names** (double underscore).
> 
> Exemples très connus :
> 
> • **name**  
> • **init**  
> • **str**  
> • **file**  
> • **dict** Il sont entourée par quatre "__"

# 8️⃣ Organisation en Package

Jusqu'ici nos modules étaient des fichiers `.py` isolés. Quand le projet grandit, on les regroupe dans un **package** : un dossier qui contient un fichier spécial `__init__.py`.

```
# Sans package — fichiers éparpillés         # Avec package — organisé
produits.py                                  stockpro/
fournisseurs.py                  →               __init__.py
commandes.py                                     produits.py
main.py                                          fournisseurs.py
                                                 commandes.py
                                             main.py
```

Le fichier `__init__.py` joue deux rôles :

- il **signale à Python** que ce dossier est un package importable
- il **définit ce qu'on expose** à l'extérieur du package

```
stockpro/
    __init__.py
    produits.py
    fournisseurs.py
    commandes.py
main.py
```

**produits.py** — gestion des produits

python

```python
def ajouter_produit(nom: str, prix: float) -> dict:
    """Crée un nouveau produit avec un stock initial à zéro."""
    return {"nom": nom, "prix": prix, "stock": 0}

def afficher_produit(produit: dict) -> None:
    print(f"{produit['nom']} — {produit['prix']:.2f} € (stock : {produit['stock']})")
```

**fournisseurs.py** — gestion des fournisseurs

python

```python
def get_fournisseur(nom: str) -> dict:
    """Retourne les infos d'un fournisseur."""
    return {"nom": nom, "contact": f"contact@{nom.lower()}.com"}
```

**commandes.py** — gestion des commandes

python

```python
from .produits     import ajouter_produit   # import relatif : . = dossier courant
from .fournisseurs import get_fournisseur   # import relatif : . = dossier courant

def passer_commande(nom_produit: str, prix: float, nom_fournisseur: str) -> dict:
    """Crée une commande en associant un produit et un fournisseur."""
    produit     = ajouter_produit(nom_produit, prix)
    fournisseur = get_fournisseur(nom_fournisseur)
    return {"produit": produit, "fournisseur": fournisseur, "statut": "en cours"}
```

****init**.py** — point d'entrée du package

python

```python
# On importe uniquement ce qu'on veut rendre accessible de l'extérieur.
# L'utilisateur du package n'a pas à connaître l'organisation interne des fichiers.

from .produits  import ajouter_produit
from .commandes import passer_commande

__all__ = ["ajouter_produit", "passer_commande"]
# fournisseurs et afficher_produit ne sont pas exposés — usage interne uniquement
```

**main.py** — utilisation du package

Ajouter le model à PYTHONPATH:

```python
$env:PYTHONPATH = "C:\Users\DELL\Desktop\mon code\stockpro"
```

python

```python
from stockpro import ajouter_produit, passer_commande

# Créer un produit
p = ajouter_produit("Clavier", 49.99)
print(p)
# → {'nom': 'Clavier', 'prix': 49.99, 'stock': 0}

# Passer une commande

print(cmd)
# → {'produit': {'nom': 'Souris', 'prix': 29.99, 'stock': 0},
#    'fournisseur': {'nom': 'Logitech', 'contact': 'contact@logitech.com'},
#    'statut': 'en cours'}
```

> 💡 Depuis `main.py`, on importe depuis `stockpro` sans savoir dans quel fichier se trouvent les fonctions. C'est le rôle de `__init__.py` : **masquer la complexité interne** et offrir une interface simple.

# 1️⃣0️⃣ Import relatif

```python
"""
Le point (.) désigne le package courant.
.. désigne le package parent.
Utilisé uniquement à l'intérieur d'un package.
"""

# stockpro/commandes.py
from .produits      import ajouter_produit     # même package
from .fournisseurs  import get_fournisseur      # même package
```

# 1️⃣1️⃣ Module paramétré — configurer un module à l'import

Un module peut exposer un **comportement configurable** : plutôt que de coder en dur ses constantes, il accepte des paramètres au moment de son initialisation. C'est le pont entre un simple fichier `.py` et un module réutilisable dans plusieurs contextes.

```
stockpro/
    alertes.py       ← module paramétré
    main.py
```

---

## Problème sans paramétrage

```python
# alertes.py — version rigide
"""
Module d'alertes StockPro.
Problème : seuil et destinataire sont codés en dur.
Si un autre projet l'importe, il hérite de ces valeurs sans pouvoir les changer.
"""

SEUIL      = 10                      # ← impossible à changer de l'extérieur
DESTINATAIRE = "admin@stockpro.fr"   # ← idem

def verifier(produits: list) -> list:
    """Retourne les produits sous le seuil d'alerte."""
    return [p for p in produits if p["stock"] < SEUIL]
```

```python
# main.py — utilisation rigide
import alertes

produits = [
    {"nom": "Crayon HB",  "stock": 5},
    {"nom": "Stylo Bleu", "stock": 50},
    {"nom": "Gomme",      "stock": 2},
]

# Impossible de passer seuil=20 sans modifier alertes.py directement
en_alerte = alertes.verifier(produits)
for p in en_alerte:
    print(f"⚠️  {p['nom']} — stock critique")
```

```
⚠️  Crayon HB — stock critique
⚠️  Gomme — stock critique
```

- **le module est rigide** : chaque projet qui l'importe est forcé d'utiliser `seuil=10`
- **mauvaise pratique** : modifier `alertes.py` pour changer le seuil affecte tous les projets qui l'utilisent
- **solution** : rendre le module configurable via une **fonction d'initialisation**

---

## Patron 1 — Fonction `configurer()` (le plus simple)

Le module expose une fonction `configurer()` à appeler **une seule fois** avant utilisation. C'est le patron le plus lisible pour des débutants.

```python
# alertes.py — version paramétrée
"""
Module d'alertes StockPro — paramétrable.
Appeler configurer() avant tout usage pour adapter le comportement.
"""

# Valeurs par défaut — utilisées si configurer() n'est pas appelé
_seuil_global      = 10
_destinataire_global = "admin@stockpro.fr"


def configurer(seuil: int = 10, destinataire: str = "admin@stockpro.fr") -> None:
    """
    Initialise le module avec les paramètres du projet appelant.

    Args:
        seuil        : quantité minimale avant alerte (défaut : 10)
        destinataire : adresse email pour les notifications (défaut : admin)

    À appeler UNE SEULE FOIS au démarrage de l'application.
    """
    global _seuil_global, _destinataire_global   # on modifie les variables du module
    _seuil_global        = seuil
    _destinataire_global = destinataire
    print(f"✅ Module alertes configuré — seuil={seuil} | destinataire={destinataire}")


def verifier(produits: list) -> list:
    """Retourne les produits dont le stock est sous le seuil configuré."""
    return [p for p in produits if p["stock"] < _seuil_global]


def rapport(produits: list) -> None:
    """Affiche le rapport d'alertes avec le seuil actif."""
    en_alerte = verifier(produits)
    print(f"\n=== Rapport Alertes StockPro (seuil : {_seuil_global}) ===")
    if not en_alerte:
        print("  ✅ Aucun produit en rupture")
    for p in en_alerte:
        print(f"  ⚠️  {p['nom']:20} stock={p['stock']:>4}  → notifier {_destinataire_global}")
    print(f"  {len(en_alerte)} alerte(s) détectée(s)")
```

```python
# main.py — utilisation paramétrée

Démonstration : le même module alertes utilisé avec deux configurations différentes.
"""

produits = [
    {"nom": "Crayon HB",     "stock":  5},
    {"nom": "Stylo Bleu",    "stock": 50},
    {"nom": "Gomme",         "stock":  2},
    {"nom": "Rame Papier A4","stock": 15},

# ── Configuration pour l'entrepôt principal ──────────────────────────────

# ── Reconfiguration pour une boutique avec seuil différent ───────────────
```

- **`global _seuil_global`** : déclare qu'on modifie la variable du module (pas une variable locale) — sans `global`, l'affectation créerait une variable locale sans effet
- **`configurer()` avant tout appel** : convention claire — le module sait que ses paramètres sont prêts
- **valeurs par défaut dans `configurer()`** : le module reste fonctionnel même sans appeler `configurer()` — comportement de repli garanti

## Patron 2 — Paramètres dans les fonctions (le plus flexible)

Chaque fonction reçoit ses paramètres directement. Aucune configuration globale — zéro état partagé.

```python
# alertes_v2.py — version sans état global
"""
Module d'alertes sans état global.
Les paramètres sont passés à chaque appel — totalement sans effet de bord.
"""

def verifier(produits: list, seuil: int = 10) -> list:
    """
    Retourne les produits sous le seuil donné.

    Args:
        produits : liste de dicts avec clé 'stock'
        seuil    : quantité minimale (défaut : 10)
    """
    return [p for p in produits if p["stock"] < seuil]


def rapport(produits: list, seuil: int = 10, destinataire: str = "admin@stockpro.fr") -> None:
    """Affiche le rapport d'alertes pour le seuil donné."""
    en_alerte = verifier(produits, seuil=seuil)
    print(f"\n=== Rapport Alertes (seuil : {seuil}) ===")
    for p in en_alerte:
        print(f"  ⚠️  {p['nom']:20} stock={p['stock']:>4}  → {destinataire}")
    print(f"  {len(en_alerte)} alerte(s)")
```

```python
# main.py — appels avec paramètres explicites
import alertes_v2 as alertes

produits = [
    {"nom": "Crayon HB",     "stock":  5},
    {"nom": "Stylo Bleu",    "stock": 50},
    {"nom": "Gomme",         "stock":  2},
    {"nom": "Rame Papier A4","stock": 15},
]

# Chaque appel est indépendant — pas d'état partagé entre les deux
alertes.rapport(produits, seuil=10, destinataire="entrepot@stockpro.fr")
alertes.rapport(produits, seuil=20, destinataire="boutique@stockpro.fr")
```

**Comparaison des deux patrons :**

|                                             | Patron 1 — `configurer()`        | Patron 2 — Paramètres directs    |
| ------------------------------------------- | -------------------------------- | -------------------------------- |
| **Syntaxe**                                 | `configurer()` puis `verifier()` | `verifier(produits, seuil=20)`   |
| **État global**                             | Oui (`_seuil_global`)            | Non                              |
| **Appels multiples avec seuils différents** | Nécessite re-configurer          | Naturel                          |
| **Lisibilité**                              | Configuration centralisée claire | Intention visible à chaque appel |
| **Cas d'usage**                             | Config fixe au démarrage (app)   | Besoins variables (librairie)    |

## Patron 3 — `__init__.py` paramétré pour un package

Quand le module devient un package, `__init__.py` joue le rôle de point de configuration central.

```
stockpro/
    __init__.py      ← configure le package à l'import
    alertes.py
    rapports.py
    main.py
```

```python
# stockpro/__init__.py
"""
Package StockPro — point d'entrée et configuration.
Les paramètres passés ici s'appliquent à tout le package.
"""

from stockpro import alertes, rapports

# Configuration par défaut du package
_config = {
    "seuil_alerte" : 10,
    "devise"       : "TND",
    "debug"        : False,
}


def configurer(**kwargs) -> None:
    """
    Configure le package StockPro.

    Usage:
        import stockpro
        stockpro.configurer(seuil_alerte=20, devise="EUR", debug=True)

    Paramètres acceptés:
        seuil_alerte (int)  : seuil de rupture de stock
        devise       (str)  : devise pour l'affichage des prix
        debug        (bool) : active les logs détaillés
    """
    cles_invalides = set(kwargs) - set(_config)
    if cles_invalides:
        raise ValueError(f"Paramètres inconnus : {cles_invalides}. "
                         f"Valides : {set(_config)}")
    _config.update(kwargs)
    if _config["debug"]:
        print(f"[DEBUG] StockPro configuré : {_config}")


def get_config(cle: str):
    """Retourne la valeur d'un paramètre de configuration."""
    if cle not in _config:
        raise KeyError(f"Paramètre inconnu : {cle!r}")
    return _config[cle]
```

```python
# stockpro/alertes.py — utilise la config du package
"""
Module alertes — lit sa configuration depuis le package parent.
"""

from stockpro import get_config


def verifier(produits: list) -> list:
    """Utilise le seuil configuré dans stockpro.configurer()."""
    seuil = get_config("seuil_alerte")   # ← lit la config centrale
    return [p for p in produits if p["stock"] < seuil]
```

```python
# main.py — configuration unique, propagée à tout le package
"""
Un seul appel configurer() → tout le package StockPro est paramétré.
"""

import stockpro

# Configuration unique au démarrage
stockpro.configurer(seuil_alerte=20, devise="TND", debug=True)

produits = [
    {"nom": "Crayon HB",  "stock":  5},
    {"nom": "Stylo Bleu", "stock": 50},
    {"nom": "Gomme",      "stock": 15},
]

# Tous les modules du package utilisent seuil=20 automatiquement
en_alerte = stockpro.alertes.verifier(produits)

devise = stockpro.get_config("devise")
for p in en_alerte:
    print(f"⚠️  {p['nom']} — stock critique ({devise})")
```

```
[DEBUG] StockPro configuré : {'seuil_alerte': 20, 'devise': 'TND', 'debug': True}
⚠️  Crayon HB — stock critique (TND)
⚠️  Gomme — stock critique (TND)
```

- **`_config.update(kwargs)`** : met à jour uniquement les clés passées — les autres gardent leur valeur par défaut
- **validation des clés inconnues** : `set(kwargs) - set(_config)` détecte les fautes de frappe dans les paramètres (`seuil_alerr` → erreur claire)
- **`get_config()`** : interface d'accès centralisée — n'importe quel module du package lit la même configuration

## Récapitulatif — Quand utiliser quel patron

```
Mon module a des paramètres qui ne changent pas en cours d'exécution
(ex : config de connexion, seuil global d'une application)
    → Patron 1 : configurer() appelé une fois au démarrage

Mes fonctions peuvent être appelées avec des paramètres différents
(ex : bibliothèque réutilisable, calculs avec seuils variables)
    → Patron 2 : paramètres directs dans chaque fonction

Le projet est organisé en package avec plusieurs modules liés
(ex : StockPro avec alertes + rapports + services)
    → Patron 3 : __init__.py paramétré, config propagée au package
```

| Patron             | Syntaxe d'appel                                           | État partagé  | Cas d'usage                  |
| ------------------ | --------------------------------------------------------- | ------------- | ---------------------------- |
| `configurer()`     | `module.configurer(seuil=20)` puis `module.verifier(p)`   | Oui           | Application avec config fixe |
| Paramètres directs | `module.verifier(p, seuil=20)`                            | Non           | Bibliothèque réutilisable    |
| `__init__.py`      | `pkg.configurer(seuil=20)` · tous les modules en héritent | Oui (package) | Package multi-modules        |

- **`services.py`** : sait quoi faire avec ces données (logique métier)
- **`run.py`** : point d'entrée, en dehors du package, orchestre le tout

**`services.py`** — couche logique métier

Importe les données depuis `repository.py` et applique des règles métier dessus.

```python
from .repository import get_produits  # . = dans le même package (stockpro/)
```

# 1️⃣2️⃣ Rechargement d'un module

Normalement, Python charge un module **une seule fois** en mémoire. Si vous modifiez le fichier pendant l'exécution (en développement interactif, dans un notebook), Python ne recharge pas automatiquement la nouvelle version. `importlib.reload()` force ce rechargement sans relancer l'interpréteur.

python

```python
import importlib
import stockpro.repository as repo

# On modifie repository.py à la main, puis on force le rechargement :
importlib.reload(repo)

# repo.get_produits() utilise maintenant la nouvelle version ✅
print(repo.get_produits())
```

⚠️ **Piège classique** : si vous avez déjà fait `from stockpro.repository import get_produits`, recharger le module ne met **pas** à jour cette référence — elle pointe toujours vers l'ancienne version.

python

```python
from stockpro.repository import get_produits  # référence directe

importlib.reload(repo)  # recharge le module...
get_produits()          # ...mais cette variable pointe encore l'ancienne version ❌

repo.get_produits()     # celle-ci est à jour ✅
```

> 💡 En pratique : `reload()` est utile dans un notebook Jupyter ou un REPL. Dans un projet normal, on relance simplement le script.

# 1️⃣3️⃣ Éviter les imports circulaires

Un import circulaire se produit quand deux modules s'importent mutuellement. Python ne peut pas résoudre ce cycle et lève une erreur.

```
stockpro/
    produits.py    ← importe commandes
    commandes.py   ← importe produits   → CYCLE ❌
```

python

```python
# produits.py
from .commandes import passer_commande   # importe commandes

# commandes.py
from .produits import get_produit        # importe produits → ImportError
```

**Solution 1 — import local dans la fonction** : on diffère l'import au moment où la fonction est appelée, pas au chargement du module.

python

```python
# commandes.py
def passer_commande(nom_produit: str, prix: float) -> dict:
    from .produits import get_produit   # importé seulement à l'appel ✅
    produit = get_produit(nom_produit, prix)
    return {"produit": produit, "statut": "en cours"}
```

**Solution 2 — extraire dans un troisième module** (recommandée) : la logique partagée va dans un module neutre que les deux peuvent importer sans cycle.

```
stockpro/
    modeles.py     ← données partagées, n'importe personne
    produits.py    ← importe modeles
    commandes.py   ← importe modeles
```

python

```python
# modeles.py — aucun import interne
def creer_produit(nom: str, prix: float) -> dict:
    return {"nom": nom, "prix": prix, "stock": 0}

# produits.py
from .modeles import creer_produit   # pas de cycle ✅

# commandes.py
from .modeles import creer_produit   # pas de cycle ✅
```

# 1️⃣4️⃣ Module de configuration professionnel

Dans un projet réel, les paramètres changent selon l'environnement (développement, production, tests). Coder ces valeurs en dur dans les modules est une mauvaise pratique — elles doivent être centralisées dans un `config.py` qui les lit depuis les variables d'environnement.

```
stockpro/
    config.py    ← toutes les constantes au même endroit
    services.py  ← consomme la config
```

**`config.py`**

python

```python
import os

# os.getenv("NOM", "valeur_par_defaut")
# → lit la variable d'environnement NOM
# → retourne la valeur par défaut si elle n'existe pas

DEBUG        = os.getenv("DEBUG", "False") == "True"
SEUIL_ALERTE = int(os.getenv("SEUIL_ALERTE", "50"))
TVA          = float(os.getenv("TVA", "0.20"))
```

**`services.py`**

python

```python
from .config import DEBUG, SEUIL_ALERTE

def produits_en_alerte(produits: list) -> list:
    if DEBUG:
        print(f"[DEBUG] Seuil actif : {SEUIL_ALERTE}")  # affiché seulement en dev
    return [p for p in produits if p["stock"] < SEUIL_ALERTE]
```

powershell

```powershell

$env:SEUIL_ALERTE = "100"

# Affiche → [DEBUG] Seuil actif : 100
```

> 💡 Avantage : on change le comportement de l'application **sans modifier le code** — juste en changeant une variable d'environnement.

# 1️⃣5️⃣ Tests internes avec `__main__`

On a vu en section 6 que le bloc `if __name__ == "__main__"` ne s'exécute pas à l'import. On peut l'utiliser pour placer des tests rapides directement dans le module, sans avoir besoin d'un fichier de test séparé.

`assert` vérifie une condition et lève une erreur si elle est fausse — c'est le moyen le plus simple de valider un résultat.

python

```python
# stockpro/services.py

from .repository import get_produits

def valeur_stock(produits: list) -> float:
    """Calcule prix × stock pour chaque produit, retourne la somme."""
    return sum(p["prix"] * p["stock"] for p in produits)

if __name__ == "__main__":
    # Ce bloc s'exécute avec : py services.py
    # Il est ignoré quand services.py est importé depuis run.py
    produits = get_produits()

    assert len(produits) > 0,        "❌ Aucun produit retourné"
    assert valeur_stock(produits) > 0, "❌ Valeur totale nulle"

    print("✅ Tests internes validés")
    print(f"   Valeur totale : {valeur_stock(produits):.2f} €")
```

powershell

```powershell
py stockpro/services.py
# → ✅ Tests internes validés
# → Valeur totale : 15 546,15 €
```

# 1️⃣7️⃣ Conventions de nommage

Le nommage des fichiers Python suit des règles précises. Un mauvais nom peut provoquer des erreurs silencieuses difficiles à diagnostiquer.

| Règle                                | Correct              | Incorrect            |
| ------------------------------------ | -------------------- | -------------------- |
| Utiliser `snake_case`                | `gestion_stock.py`   | `GestionStock.py`    |
| Pas de tirets                        | `produit_service.py` | `produit-service.py` |
| Ne pas masquer les modules standards | `calculs.py`         | `math.py`            |
| Nom descriptif                       | `stock_service.py`   | `utils.py`           |

**Pourquoi ne pas nommer un fichier `math.py` ?**

python

```python
# Si vous créez math.py dans votre projet :
import math
print(math.pi)   # ← charge VOTRE math.py, pas le module standard
                 # AttributeError: module 'math' has no attribute 'pi' ❌
```

Python cherche d'abord dans le répertoire courant — votre fichier masque le module standard.

# 1️⃣8️⃣ Bonnes pratiques — récapitulatif

Ces règles résument tout ce qu'on a vu. Elles s'appliquent à tout projet Python sérieux.

**Organisation**

- Séparer `repository` (accès aux données) et `services` (logique métier)
- Centraliser la configuration dans `config.py` avec `os.getenv`
- Un `__init__.py` propre qui n'expose que l'API publique via `__all__`

**Imports**

- Préférer l'import absolu (`from stockpro.services import ...`) — plus lisible
- Utiliser l'import relatif (`.module`) uniquement à l'intérieur d'un package
- Ne jamais faire `from module import *` — risque de collision silencieuse

**Qualité**

- Documenter chaque module avec une docstring en tête de fichier
- Ne jamais exécuter de logique au niveau global — tout encapsuler dans des fonctions
- Nommer les fichiers en `snake_case`, sans conflit avec les modules standards

# 1️⃣9️⃣ Package avancé avec classes — modèle objet

Jusqu'ici nos produits étaient des dictionnaires. Dans un projet réel, on utilise des **classes** pour représenter les entités métier. On ajoute une couche `models/` qui contient ces classes.

```
stockpro/
    __init__.py
    models/
        __init__.py
        produit.py       ← définit la classe Produit
    repository/
        __init__.py
        produit_repo.py  ← retourne des objets Produit
    services/
        __init__.py
        stock_service.py ← logique métier sur des objets Produit
run.py
```

**`models/produit.py`** — définition de la classe

python

```python
class Produit:
    def __init__(self, nom: str, prix: float, stock: int):
        self.nom   = nom
        self.prix  = prix
        self.stock = stock

    def valeur(self) -> float:
        """Retourne prix × stock."""
        return self.prix * self.stock

    def __repr__(self) -> str:
        """Représentation lisible pour print()."""
        return f"Produit({self.nom}, {self.prix}€, stock={self.stock})"
```

**`repository/produit_repo.py`** — retourne des objets Produit

python

```python
from ..models.produit import Produit   # .. = remonter d'un niveau (stockpro/)

def get_all() -> list:
    return [
        Produit("Clavier", 49.99, 120),
        Produit("Souris",  29.99,  85),
        Produit("Écran",  249.99,  30),
    ]
```

**`services/stock_service.py`** — logique métier

python

```python
from ..repository.produit_repo import get_all

def valeur_totale() -> float:
    return sum(p.valeur() for p in get_all())  # appelle la méthode de la classe

def alertes(seuil: int = 50) -> list:
    return [p for p in get_all() if p.stock < seuil]
```

**`run.py`**

python


# 2️⃣0️⃣ Module interne vs bibliothèque externe

Quand on fait `import something`, Python peut trouver deux types de modules très différents :

|             | Module interne         | Bibliothèque externe |
| ----------- | ---------------------- | -------------------- |
| Origine     | Votre projet           | Installée via `pip`  |
| Emplacement | Votre dossier          | `site-packages/`     |
| Exemple     | `stockpro/services.py` | `requests`, `pandas` |

python

```python
# Vérifier d'où vient un module
import stockpro.services as svc
import requests

print(svc.__file__)       # C:\...\mon code\stockpro\services.py
print(requests.__file__)  # C:\...\Python313\site-packages\requests\__init__.py
```

powershell

```powershell
pip list              # lister toutes les bibliothèques installées
pip show requests     # détails sur une bibliothèque précise
pip install requests  # installer une nouvelle bibliothèque
```

> 💡 Si `pip show mon_module` ne trouve rien, c'est un module interne — il vit dans votre projet, pas dans Python.

# 2️⃣1️⃣ Synthèse

Voici les concepts fondamentaux à retenir, du plus simple au plus avancé.

| Concept         | Ce que c'est                               | Exemple                             |
| --------------- | ------------------------------------------ | ----------------------------------- |
| Module          | Un fichier `.py`                           | `services.py`                       |
| Package         | Un dossier avec `__init__.py`              | `stockpro/`                         |
| `__init__.py`   | Définit l'API publique du package          | `from .services import ...`         |
| Import absolu   | Chemin complet depuis la racine            | `from stockpro.services import ...` |
| Import relatif  | Chemin depuis le fichier courant           | `from .repository import ...`       |
| `__all__`       | Liste ce qu'on expose à l'extérieur        | `__all__ = ["ajouter_produit"]`     |
| `__name__`      | Vaut `"__main__"` si lancé directement     | `if __name__ == "__main__":`        |
| `PYTHONPATH`    | Indique à Python où chercher les modules   | `$env:PYTHONPATH = "C:\..."`        |
| `site-packages` | Dossier d'installation des packages pip    | `pandas`, `openpyxl`, `requests`    |
| `venv`          | Environnement isolé par projet             | `python -m venv .venv`              |
| `__pycache__`   | Cache bytecode compilé des modules         | `services.cpython-313.pyc`          |
| `config.py`     | Centralise les constantes de configuration | `SEUIL = os.getenv(...)`            |
| `repository`    | Couche accès aux données                   | `get_produits()`                    |
| `services`      | Couche logique métier                      | `produits_en_alerte()`              |

```python
# facturation/calculs.py
"""
Calculs de facturation StockPro.
"""

def calculer_ttc(prix_ht: float, taux_tva: float = 0.20) -> float:
    """Calcule le prix TTC depuis un prix HT."""
    return round(prix_ht * (1 + taux_tva), 2)

def appliquer_remise(prix: float, taux: float) -> float:
    """Applique une remise. taux entre 0 et 1."""
    return round(prix * (1 - taux), 2)
```

```python
# facturation/rapport.py
"""
Génération de rapports de facturation.
"""

from .calculs import calculer_ttc, appliquer_remise

def generer_rapport(produits: list) -> None:

        print(f"  {p['nom']:20} HT: {p['prix_ht']:.2f}€  TTC: {ttc:.2f}€")
```
