## 1️⃣ Pourquoi modulariser un projet ?

Dans un projet réel :

- Séparation des responsabilités

- Réduction du couplage

- Réutilisabilité

- Maintenabilité

- Tests unitaires simplifiés

- Déploiement structuré

Un module est une unité logique de code.  
Un package est un regroupement hiérarchique de modules.

---

## 2️⃣ Module : définition concrète

Un module est simplement un fichier `.py`.

Exemple dans un scénario de gestion de stock : un module pour les opérations basiques sur les produits.

Contenu de **operations.py** :

```python
"""
Module d'opérations mathématiques de base pour la gestion de stock.
Ce module expose des fonctions réutilisables.
"""

def somme(a, b):
    return a + b

def produit(a, b):
    return a * b

PI = 3.14159
```

Utilisation dans un script principal pour calculer des totaux de stock :

```python
"""
Script principal utilisant le module operations pour gérer un stock.
"""

import operations

print("Somme de quantités :", operations.somme(4, 5))
print("Produit pour prix total :", operations.produit(3, 6))
print("Constante PI pour calculs :", operations.PI)
```

## 3️⃣ Les différentes formes d'import

### Import complet

```python
import math

print(math.sqrt(16))
```

### Import ciblé

```python
from math import sqrt

print(sqrt(25))
```

### Import avec alias

```python
import math as m

print(m.pi)
```

### Import élément avec alias

```python
from math import sqrt as racine

print(racine(36))
```

Éviter :

```python
from math import *
```

Risque de pollution d’espace de noms.

## 4️⃣ Espace de noms (namespace)

Chaque module possède son propre espace de noms.

Exemple dans un scénario de gestion de stock : deux modules pour différents aspects du stock.

Arborescence :

```
stock_app/
    moduleA.py
    moduleB.py
    main.py
```

Contenu de **moduleA.py** :

```python
x = 10  # Quantité en stock A
```

Contenu de **moduleB.py** :

```python
x = 20  # Quantité en stock B
```

Script principal **main.py** :

```python
import moduleA
import moduleB

print("Stock A :", moduleA.x)
print("Stock B :", moduleB.x)
```

Les variables ne se chevauchent pas.

## 6️⃣ Module exécutable vs importable

Exemple dans un scénario de calcul de stock.

Contenu de **calcul.py** :

```python
"""
Module pour calculs de stock pouvant être exécuté ou importé.
"""

def carre(x):
    return x * x

if __name__ == "__main__":
    print("Test interne de stock :", carre(5))
```

Si exécuté directement :

```
python calcul.py
```

Le test s’affiche.

Si importé dans un script de gestion :

```python
import calcul

print("Carré pour surface de stock :", calcul.carre(3))
```

Le bloc principal ne s’exécute pas.

## 7️⃣ Organisation en Package

Structure recommandée pour un package de gestion de clients dans une app e-commerce :

```
gestion/
    __init__.py
    clients.py
    produits.py
    commandes.py
```

Contenu de **gestion/clients.py** :

```python
def ajouter_client(nom):
    return f"Client {nom} ajouté"
```

Contenu de **gestion/__init__.py** (démonstration approfondie) :

```python
# __init__.py initialise le package et peut importer des éléments pour une exposition facile.
# Il définit le namespace du package et permet des imports relatifs.
# Sans __init__.py (en Python 3.3+), c'est un namespace package, mais avec, il permet du code d'initialisation.
# Exemple : importer automatiquement des fonctions clés pour simplifier l'usage.

from .clients import ajouter_client

print("Package gestion initialisé")  # Exécuté lors du premier import du package
```

Utilisation dans un script principal :

```python
from gestion import ajouter_client

print(ajouter_client("Bechir"))
```

Démonstration de __init__.py : Le print s'exécute lors de l'import, montrant son rôle d'initialisation. Il peut aussi contenir des configurations ou des hooks pour le package entier.

## 15️⃣ Structuration recommandée projet professionnel

```
project/
    src/
        myapp/
            __init__.py
            services/
            repository/
            models/
    tests/
    requirements.txt
    pyproject.toml
```

Explication de requirements.txt et pyproject.toml :  

- **requirements.txt** liste les dépendances externes installées via `pip install -r requirements.txt`. Exemple contenu : `requests==2.28.0`.  

- **pyproject.toml** est le standard moderne (PEP 518) pour la configuration du projet, incluant dépendances, build tools, et metadata. Exemple :  
  
  ```toml
  [tool.poetry]
  name = "myapp"
  version = "0.1.0"
  dependencies = { python = "^3.8", requests = "^2.28" }
  ```

## 18️⃣ Exemple avancé : Package métier

Structure pour un package e-commerce :

```
ecommerce/
    __init__.py
    cart.py
    product.py
    order.py
```

Contenu de **product.py** :

```python
class Product:
    def __init__(self, name, price):
        self.name = name
        self.price = price
```

Contenu de **cart.py** :

```python
from .product import Product

class Cart:
    def __init__(self):
        self.items = []

    def add(self, product):
        self.items.append(product)

    def total(self):
        return sum(p.price for p in self.items)
```

Utilisation :

```python
from ecommerce.cart import Cart
from ecommerce.product import Product

c = Cart()
c.add(Product("Clavier", 100))
c.add(Product("Souris", 50))

print("Total :", c.total())
```

# 1. Pourquoi éviter `from module import *` ?

### Énoncé

Pourquoi cette forme d’import peut provoquer des bugs difficiles à détecter ?

### Solution

```python
"""
Explication :
- from module import * injecte tous les noms publics dans l’espace courant.
- Risque de collision silencieuse avec des variables locales.
- Rend le code moins lisible et plus difficile à maintenir.
"""

# moduleA.py
x = 10

# moduleB.py
x = 20

# main.py
from moduleA import *
from moduleB import *

print(x)  # Quelle valeur ? 20 (moduleB écrase moduleA)
```

Conclusion : préférer import module ou import ciblé.

---

# 2. Que se passe-t-il réellement lors d’un import ?

### Énoncé

Pourquoi un module n’est exécuté qu’une seule fois ?

### Solution

```python
"""
Explication :
- Lors du premier import, Python exécute le module.
- Il est ensuite mis en cache dans sys.modules.
- Les imports suivants réutilisent l’objet déjà chargé.
"""

# demo.py
print("Module chargé")

# main.py
import demo
import demo
```

Résultat : “Module chargé” s’affiche une seule fois.

# 3. Pourquoi éviter la logique lourde au niveau global ?

### Énoncé

Pourquoi ne faut-il pas mettre du code métier directement dans le module sans protection ?

### Solution

```python
"""
Explication :
- Le code global s’exécute à chaque import.
- Peut provoquer effets de bord.
- Préférer encapsuler dans des fonctions.
"""

# mauvais.py
print("Connexion base de données")  # exécuté à chaque import
```

Bonne pratique :

```python
def initialiser():
    print("Connexion base de données")

if __name__ == "__main__":
    initialiser()
```

# 6. Pourquoi éviter les imports circulaires ?

```python
Explication :
- Python charge module A.
- A importe B.
- B importe A avant que A soit complètement initialisé.

    autre_fonction()
```

# 11. Rechargement : piège courant

### Énoncé

Pourquoi importlib.reload ne met pas toujours à jour les références ?

### Solution

```python

Explication :
- reload met à jour le module.
- Mais les objets déjà importés via from module import X restent inchangés.
"""

import importlib
import operations

importlib.reload(operations)

# somme ici reste ancienne référence
```
