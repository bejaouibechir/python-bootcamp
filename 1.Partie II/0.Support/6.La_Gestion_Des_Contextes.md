# Gestion des contextes en Python

## 1.1 Définition opérationnelle

Un **contexte** représente une phase contrôlée d’exécution durant laquelle :

- Une ressource est acquise

- Elle est utilisée

- Elle est libérée proprement

Un gestionnaire de contexte automatise ce cycle :

Acquisition → Utilisation → Libération

---

## 1.2 Problématique réelle

Contexte métier :  
Système de facturation qui écrit des transactions dans un fichier journal.

Problème :

- Si une exception survient

- Si le développeur oublie de fermer la ressource

- Si le code évolue et que la fermeture est déplacée

La ressource reste ouverte → fuite mémoire → corruption → verrouillage OS.

---

## 1.3 Approche naïve (risque)

Créer le fichier journal transaction_logger.py :

```python
# Simulation simple d’écriture dans un fichier
# Approche risquée : oubli possible de fermeture

f = open("journal.txt", "w")

print("Ecriture transaction 1", file=f)

# Simulation d’une erreur
raise ValueError("Erreur pendant l'écriture")

# Cette ligne ne sera jamais exécutée
f.close()
```

Problème observable :

- Le fichier reste ouvert

- Le système peut conserver un verrou

- Le programme n’est pas résilient

---

## 1.4 Sécurisation avec try / finally

Créer le fichier transaction_logger_safe.py :

```python
# Utilisation de try/finally pour garantir la fermeture

f = open("journal.txt", "w")

try:
    print("Ecriture transaction 1", file=f)
    raise ValueError("Erreur pendant l'écriture")

finally:
    # Cette ligne sera toujours exécutée
    f.close()
    print("Fichier fermé proprement")
```

Comportement :

- Même en cas d’exception

- La ressource est libérée

---

## 1.5 Introduction du mot-clé with

Créer le fichier transaction_logger_with.py :

```python
# Le mot-clé with automatise le cycle ouverture/fermeture

with open("journal.txt", "w") as f:
    print("Ecriture transaction 1", file=f)
    raise ValueError("Erreur pendant l'écriture")

# La fermeture est automatique
print("Bloc terminé")
```

Principe :

- **enter** → acquisition

- **exit** → libération

# 2️⃣ Fonctionnement interne d’un gestionnaire de contexte

Un objet devient gestionnaire de contexte s’il définit :

- **enter**()

- **exit**(type_exception, valeur_exception, traceback)

---

## 2.1 Implémentation contrôlée

Créer le fichier ressource_demo.py :

```python
import time

class Ressource:

    def __init__(self):
        # Initialisation de l’état
        self.etat = "Initialisation"
        print(self.etat)

    def __enter__(self):
        # Acquisition de la ressource
        self.etat = "Ressource acquise"
        print(self.etat)
        return self

    def __exit__(self, exc_type, exc_value, exc_traceback):
        # Libération systématique
        self.etat = "Ressource libérée"
        print(self.etat)

        print("Type exception:", exc_type)
        print("Valeur exception:", exc_value)

        # Retour False → propage l’exception
        return False

    def utiliser(self):
        print("Utilisation en cours...")
        time.sleep(1)
        raise ValueError("Erreur métier simulée")
```

Utilisation :

```python
with Ressource() as r:
    r.utiliser()
```

Observation :

- **enter** est appelé automatiquement

- **exit** est appelé même en cas d’erreur

- L’exception est propagée car **exit** retourne False

# 3️⃣ Contrôle de propagation des exceptions

```python
class RessourceSilencieuse:

    def __enter__(self):
        print("Entrée contexte")
        return self

    def __exit__(self, exc_type, exc_value, exc_traceback):
        print("Sortie contexte")

        if exc_type:
            print("Exception interceptée:", exc_value)
            return True  # supprime l'exception

        return False
```

Test :

```python

```

Résultat :

- L’exception est absorbée

- Le flux continue

# 4️⃣ Cas métier complet : Connexion simulée base de données

Créer le fichier db_context.py :

```python
class ConnexionDB:

    def __init__(self, nom):
        self.nom = nom
        self.connectee = False

    def __enter__(self):
        # Simulation connexion
        self.connectee = True
        print(f"Connexion à {self.nom}")
        return self

    def executer(self, requete):
        if not self.connectee:
            raise RuntimeError("Connexion non active")

        print("Execution requête:", requete)

    def __exit__(self, exc_type, exc_value, exc_traceback):
        # Fermeture systématique
        self.connectee = False
        print("Connexion fermée")

        return False
```

Utilisation :

```python
with ConnexionDB("PostgreSQL") as db:
    db.executer("SELECT * FROM clients")
```

## Solution

```python
"""
Explication
- try/finally dépend de la discipline du développeur.
- with délègue la responsabilité au protocole de contexte.
- Dans un projet réel, with réduit drastiquement les oublis.

    with open("journal_with.txt", "w") as f:

```

# 20️⃣ Peut-on chaîner des contextes dynamiquement ?

## Solution

Créer le fichier dynamic_context.py :

```python
from contextlib import ExitStack

"""
Explication
- ExitStack permet gestion dynamique
  d’un nombre variable de contextes.
"""

class Demo:

    def __init__(self, nom):
        self.nom = nom

    def __enter__(self):
        print("Entrée", self.nom)
        return self

    def __exit__(self, a, b, c):
        print("Sortie", self.nom)

from contextlib import ExitStack

with ExitStack() as stack:
    for nom in ["A", "B", "C"]:
        stack.enter_context(Demo(nom))
    print("Bloc principal")
```
